# [알고리즘] 그리디 개념

## 1. 한 줄 요약

> 그리디는 매 단계에서 지금 가장 좋아 보이는 선택을 고르고, 그 선택을 되돌리지 않은 채 답을 만들어 가는 알고리즘입니다.

---

## 2. 선수 지식

- 정렬: 가장 작은 값, 가장 큰 값, 빠른 종료 시간처럼 선택 기준을 만들 때 자주 사용합니다.
- 반복문: 현재 상태에서 선택하고 남은 문제로 이동하는 과정을 반복합니다.
- 우선순위 큐: 매번 가장 작은 값이나 가장 큰 값을 빠르게 꺼낼 때 사용합니다.
- 최적해: 가능한 답 중 문제 조건을 가장 잘 만족하는 답입니다.
- 부분 문제: 전체 문제를 구성하는 작은 문제입니다.
- 반례: 어떤 풀이가 항상 맞지 않음을 보여 주는 예외 입력입니다.

---

## 3. 어떤 문제를 해결하기 위해 사용하는가?

그리디는 모든 경우를 다 살펴보지 않고도 답을 빠르게 구하고 싶을 때 사용합니다.

### 기존 방식의 문제

- 가능한 선택을 모두 확인하면 시간이 너무 오래 걸릴 수 있습니다.
- 매번 여러 선택지가 생기는 문제는 완전탐색으로 경우의 수가 크게 늘어납니다.
- 동적 계획법으로 풀 수 있어도, 상태를 많이 저장해야 해서 코드와 메모리가 부담될 수 있습니다.

예를 들어 일정이 여러 개 있고 최대한 많은 회의를 배정해야 한다고 해 봅시다. 모든 회의 조합을 만들어 확인하면 회의 수가 조금만 늘어도 경우가 많아집니다.

### 이 알고리즘을 사용하면

- 문제에 맞는 선택 기준만 찾으면 단순한 반복으로 풀 수 있습니다.
- 정렬 후 앞에서부터 처리하거나, 우선순위 큐에서 하나씩 꺼내는 형태가 많습니다.
- 입력이 커져도 `O(n log n)` 정도로 해결되는 경우가 자주 있습니다.

단, 그리디는 아무 문제에나 사용할 수 없습니다. 지금 가장 좋아 보이는 선택이 나중에도 손해가 되지 않는다는 근거가 있어야 합니다.

## 4. 핵심 아이디어

그리디의 핵심은 "한 번 한 선택을 믿고 앞으로 간다"입니다.

그래서 그리디를 쓰려면 보통 다음 두 가지 성질을 확인합니다.

- 탐욕적 선택 성질: 지금의 최선 선택이 전체 최적해로 가는 길에 포함될 수 있어야 합니다.
- 최적 부분 구조: 현재 선택을 한 뒤 남은 문제도 같은 방식의 작은 최적화 문제로 볼 수 있어야 합니다.

### 쉬운 비유

길게 늘어선 징검다리를 건너는데, 매번 가장 가까운 다음 돌만 밟아도 목적지까지 가장 적은 힘으로 갈 수 있는 구조라면 그리디가 잘 맞습니다.

하지만 가까운 돌을 밟으면 중간에 막다른 곳으로 가고, 조금 멀리 있는 돌을 먼저 밟아야 전체 길이 쉬워지는 구조라면 그리디는 틀릴 수 있습니다.

### 직관적으로 이해하기

물건을 상자에 담을 때 "무게가 가벼운 것부터 담으면 최대한 많이 담을 수 있다"는 조건이 성립하는 문제가 있습니다. 이때는 정렬한 뒤 가벼운 물건부터 고르면 됩니다.

반대로 "가치가 높은 조합"을 찾아야 하는데 무게와 가치가 복잡하게 섞여 있다면, 단순히 가장 비싼 물건부터 고르는 선택은 정답을 보장하지 못할 수 있습니다.

그리디는 선택 기준이 문제 구조와 정확히 맞을 때 강합니다.

## 5. 동작 과정 살펴보기

### 예제 상황

5000원을 정해진 지폐와 동전으로 거슬러 주려고 합니다.

사용 가능한 단위가 `[1000, 500, 100, 50, 10]`이고, 큰 단위가 작은 단위들의 조합으로 자연스럽게 대체될 수 있다고 가정합니다. 이때는 큰 단위부터 최대한 사용하는 그리디가 잘 맞습니다.

### 예제 입력

```text
amount = 2860
units = [1000, 500, 100, 50, 10]
```

### 예제 출력

```text
8
```

### 단계별 동작

1. 가장 큰 단위인 1000부터 확인합니다.
2. 2860원에서 1000원을 2개 사용할 수 있으므로 남은 금액은 860원이 됩니다.
3. 500원을 1개 사용하면 남은 금액은 360원이 됩니다.
4. 100원을 3개 사용하면 남은 금액은 60원이 됩니다.
5. 50원을 1개 사용하면 남은 금액은 10원이 됩니다.
6. 10원을 1개 사용하면 남은 금액은 0원이 됩니다.
7. 사용한 개수 `2 + 1 + 3 + 1 + 1 = 8`을 답으로 반환합니다.

이 예제의 핵심은 "큰 단위를 먼저 쓰는 선택이 나중에 더 나쁜 결과를 만들지 않는다"는 점입니다.

## 7. 기본 코드 템플릿

```python
def minimum_unit_count(amount, units):
    sorted_units = sorted(units, reverse=True)
    used_count = 0
    remaining = amount

    for unit in sorted_units:
        if unit > remaining:
            continue

        count_for_unit = remaining // unit
        used_count += count_for_unit
        remaining %= unit

        if remaining == 0:
            break

    if remaining != 0:
        return -1

    return used_count


def max_non_overlapping_meetings(meetings):
    ordered_meetings = sorted(meetings, key=lambda meeting: (meeting[1], meeting[0]))
    selected_count = 0
    current_end = 0

    for start, end in ordered_meetings:
        if start >= current_end:
            selected_count += 1
            current_end = end

    return selected_count


if __name__ == "__main__":
    print(minimum_unit_count(2860, [1000, 500, 100, 50, 10]))

    schedules = [
        (1, 4),
        (3, 5),
        (5, 7),
        (6, 9),
        (8, 10),
    ]
    print(max_non_overlapping_meetings(schedules))
```

### 코드 흐름 설명

* `minimum_unit_count`는 큰 단위부터 사용할 수 있는 만큼 사용합니다.
* `remaining`은 아직 처리하지 못한 금액입니다.
* 각 단위에서 몫은 사용 개수, 나머지는 다음 단계로 넘길 금액입니다.
* `max_non_overlapping_meetings`는 회의가 빨리 끝나는 순서대로 정렬합니다.
* 빨리 끝나는 회의를 먼저 고르면 뒤에 더 많은 회의를 넣을 가능성이 커집니다.
* `current_end`는 마지막으로 선택한 회의가 끝나는 시간입니다.
* 다음 회의의 시작 시간이 `current_end` 이상이면 겹치지 않으므로 선택합니다.

## 8. 시간복잡도와 공간복잡도

### 시간복잡도

* 이미 선택 기준대로 정렬되어 있다면 단순 반복은 보통 `O(n)`입니다.
* 정렬이 필요하면 대부분 `O(n log n)`입니다.
* 우선순위 큐를 사용하면 삽입과 삭제가 각각 `O(log n)`이고, 전체적으로 `O(n log n)` 형태가 자주 나옵니다.
* 그리디는 모든 조합을 만들지 않기 때문에 완전탐색보다 빠른 경우가 많습니다.

### 공간복잡도

* 단순 반복만 사용하면 추가 공간은 `O(1)`에 가깝습니다.
* 정렬 결과를 새 리스트로 만들면 `O(n)` 공간이 필요할 수 있습니다.
* 우선순위 큐를 사용하면 후보를 저장하기 위해 `O(n)` 공간이 필요합니다.

## 9. 예제로 이해하기

이번에는 회의실 하나에 최대한 많은 회의를 배정하는 상황을 보겠습니다.

입력 데이터:

```text
meetings = [
  (2, 6),
  (1, 3),
  (3, 4),
  (5, 8),
  (7, 9)
]
```

처리 과정:

1. 회의를 끝나는 시간이 빠른 순서로 정렬합니다.
2. `(1, 3)`을 먼저 선택합니다. 현재 종료 시간은 3입니다.
3. `(3, 4)`는 시작 시간이 3이므로 바로 이어서 선택할 수 있습니다.
4. `(2, 6)`은 이미 선택한 회의와 겹치므로 건너뜁니다.
5. `(5, 8)`은 시작 시간이 5라서 선택할 수 있습니다.
6. `(7, 9)`는 `(5, 8)`과 겹치므로 건너뜁니다.

최종 결과:

```text
선택한 회의 수 = 3
```

이 문제에서 "가장 빨리 끝나는 회의"를 고르는 이유는 남은 시간 구간을 최대한 넓게 남기기 위해서입니다. 현재 회의가 빨리 끝날수록 뒤에서 선택할 수 있는 후보가 많아집니다.

## 10. 문제에서 이 알고리즘을 떠올리는 신호

* "최소 개수", "최대 개수", "최소 비용", "최대 이익" 같은 최적화 표현이 있습니다.
* 매 단계에서 가장 큰 값, 가장 작은 값, 가장 빠른 종료 시간처럼 뚜렷한 선택 기준이 보입니다.
* 정렬한 뒤 앞에서부터 처리하면 될 것 같은 구조입니다.
* 한 번 선택한 결과를 나중에 다시 바꾸지 않아도 될 것 같습니다.
* 문제 조건에 배수 관계, 오름차순 제공, 겹치지 않는 구간 선택 같은 제한이 있습니다.
* 우선순위 큐로 매번 가장 유리한 후보를 꺼내야 할 것 같습니다.
* 크루스칼, 허프만 코딩, 회의실 배정, 거스름돈 같은 대표 유형과 닮아 있습니다.

## 11. 비슷한 알고리즘과 헷갈리는 부분

### 그리디와 동적 계획법

그리디는 지금 선택을 확정하고 되돌리지 않습니다. 동적 계획법은 여러 가능성을 저장하며 비교합니다.

어떤 선택이 미래에 영향을 크게 준다면 동적 계획법이 필요할 수 있습니다.

### 그리디와 완전탐색

완전탐색은 가능한 모든 경우를 확인합니다. 그리디는 선택 기준에 따라 한 방향으로만 진행합니다.

그리디가 맞는 근거가 없으면 완전탐색이나 백트래킹으로 반례를 확인해 보는 것이 좋습니다.

### 그리디와 정렬

정렬은 그리디를 구현하기 위한 도구인 경우가 많습니다. 정렬했다고 모두 그리디는 아닙니다.

정렬 기준이 왜 최적해를 보장하는지 설명할 수 있어야 합니다.

### 그리디와 우선순위 큐

우선순위 큐는 매 순간 가장 좋은 후보를 빠르게 꺼내는 자료구조입니다. 후보가 계속 추가되거나 바뀌는 그리디 문제에서 자주 사용합니다.

## 12. 자주 하는 실수

* 지금 가장 좋아 보이는 선택이 항상 정답이라고 바로 가정합니다.
* 반례를 확인하지 않고 그리디로 제출합니다.
* 정렬 기준을 잘못 잡아 선택 순서가 틀어집니다.
* 최소를 구해야 하는데 최대 기준으로 정렬하거나, 반대로 처리합니다.
* 선택 후 상태 갱신을 빠뜨려 같은 후보를 여러 번 사용합니다.
* 동전 문제처럼 보인다고 항상 큰 단위부터 고르면 된다고 생각합니다.
* 우선순위 큐가 필요한 문제에서 매번 리스트를 다시 정렬해 시간 초과를 만듭니다.
* 그리디 조건이 깨지는 문제를 DP나 탐색으로 바꾸지 않고 억지로 처리합니다.

## 13. 힌트 생성용 관점

### 1단계 힌트: 개념 힌트

이 문제는 모든 경우를 비교하기보다, 매 단계에서 하나의 선택을 확정할 수 있는지 확인해야 합니다. 어떤 기준으로 고르면 남은 문제에도 손해가 없는지 생각해 보세요.

### 2단계 힌트: 접근 힌트

후보들을 선택 기준에 맞게 정렬해 보세요. "가장 먼저 처리해야 하는 후보"가 무엇인지 정하면 반복문으로 앞에서부터 처리할 수 있습니다.

### 3단계 힌트: 구현 힌트

정렬된 후보를 순회하면서 선택 가능한지 조건문으로 검사하세요. 선택했다면 현재 상태를 갱신하고, 선택할 수 없다면 건너뜁니다. 후보가 계속 변한다면 우선순위 큐 사용을 고려하세요.

## 14. 언제 사용하면 좋은가

* 입력 조건: 모든 경우를 탐색하기에는 크지만, 명확한 선택 기준이 있을 때 좋습니다.
* 문제 유형: 거스름돈, 회의실 배정, 최소 신장 트리, 작업 스케줄링, 압축 코드 구성 같은 문제에서 자주 등장합니다.
* 자주 등장하는 표현: "가장 적게", "가장 많이", "최소 비용", "최대 수익", "겹치지 않게", "가능한 한 빨리" 같은 표현이 단서가 됩니다.
* 적합한 자료구조: 정렬된 리스트, 우선순위 큐, 유니온 파인드가 함께 쓰일 수 있습니다.
* 사용하면 안 되는 경우: 현재 선택이 이후 선택지를 제한해서 더 좋은 전체 해를 막는다면 그리디만으로는 위험합니다.

## 15. 요약 정리

* 그리디는 매 순간 가장 좋아 보이는 선택을 확정하는 알고리즘입니다.
* 빠르고 구현이 단순하지만, 항상 최적해를 보장하지는 않습니다.
* 탐욕적 선택 성질과 최적 부분 구조를 확인해야 합니다.
* 정렬과 우선순위 큐가 구현 도구로 자주 쓰입니다.
* 대표 시간복잡도는 정렬을 포함해 `O(n log n)`인 경우가 많습니다.
* 문제에서 최적화 목표와 선택 기준이 뚜렷하면 그리디를 의심해 볼 수 있습니다.
* 반례가 쉽게 만들어지면 DP, 탐색, 백트래킹 같은 다른 방법을 검토해야 합니다.
