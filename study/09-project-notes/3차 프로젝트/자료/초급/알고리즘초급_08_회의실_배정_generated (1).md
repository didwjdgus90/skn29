# [알고리즘] 회의실 배정

## 1. 한 줄 요약

> 회의실 배정은 끝나는 시간이 가장 빠른 회의부터 선택해, 한 회의실에서 진행할 수 있는 회의 수를 최대화하는 그리디 알고리즘입니다.

---

## 2. 선수 지식

- 정렬: 회의를 어떤 기준으로 먼저 볼지 정할 때 사용합니다.
- 그리디: 현재 가장 좋아 보이는 선택을 확정하며 답을 만드는 방법입니다.
- 구간: 시작 시간과 끝나는 시간으로 표현되는 범위입니다.
- 조건 비교: 다음 회의의 시작 시간이 이전 회의의 종료 시간 이상인지 확인합니다.
- 리스트와 튜플: `(시작, 종료)` 형태로 회의 정보를 저장합니다.

---

## 3. 어떤 문제를 해결하기 위해 사용하는가?

회의실이 하나뿐일 때, 서로 시간이 겹치지 않도록 회의를 최대한 많이 넣고 싶을 때 사용합니다.

### 기존 방식의 문제

- 가능한 회의 조합을 모두 만들어 보면 정답은 구할 수 있습니다.
- 하지만 회의 개수가 많아지면 조합 수가 너무 커집니다.
- 긴 회의를 먼저 고르면 뒤에 들어갈 수 있는 짧은 회의들을 놓칠 수 있습니다.
- 빨리 시작하는 회의를 먼저 고르는 것도 정답을 보장하지 않습니다.

예를 들어 오전 9시에 시작하는 긴 회의 하나를 고르면, 그 시간 사이에 들어갈 수 있는 짧은 회의 여러 개를 모두 포기해야 할 수 있습니다.

### 이 알고리즘을 사용하면

- 회의를 끝나는 시간 기준으로 정렬한 뒤 한 번만 순회합니다.
- 현재 회의가 끝난 뒤 시작할 수 있는 회의만 선택합니다.
- 매번 가장 빨리 끝나는 회의를 선택하므로 남은 시간을 최대한 많이 확보합니다.

---

## 4. 핵심 아이디어

회의실 배정의 핵심은 "회의가 빨리 끝날수록 뒤에 더 많은 회의를 넣을 기회가 생긴다"입니다.

그래서 선택 기준은 시작 시간이 아니라 종료 시간입니다.

### 쉬운 비유

하루에 여러 개의 택배를 직접 받아야 한다고 생각해 봅시다. 하나의 약속이 빨리 끝나면 다음 약속을 잡을 수 있는 시간이 넓어집니다. 반대로 오래 걸리는 약속을 먼저 잡으면 나머지 약속이 들어갈 자리가 줄어듭니다.

회의도 같습니다. 한 회의실에서 최대한 많은 회의를 진행하려면, 가능한 한 빨리 끝나는 회의를 먼저 확정하는 것이 유리합니다.

### 직관적으로 이해하기

두 회의가 모두 지금 선택 가능하다고 해 봅시다.

- 회의 A: 1시 시작, 6시 종료
- 회의 B: 2시 시작, 3시 종료

둘 중 하나만 고를 수 있다면 B를 고르는 것이 더 좋습니다. B는 3시에 끝나므로 3시 이후의 회의를 더 많이 이어 붙일 수 있습니다.

이 판단을 모든 회의에 반복하면 전체 회의 수를 최대화할 수 있습니다.

## 5. 동작 과정 살펴보기

### 예제 상황

하나의 상담실에 다음 상담 일정을 최대한 많이 배정하려고 합니다.

### 예제 입력

```text
meetings = [
  (1, 5),
  (2, 3),
  (3, 4),
  (4, 7),
  (6, 8),
  (8, 8)
]
```

### 예제 출력

```text
4
```

### 단계별 동작

1. 회의를 종료 시간이 빠른 순서로 정렬합니다.
2. 종료 시간이 같다면 시작 시간이 빠른 순서로 정렬합니다.
3. 가장 빨리 끝나는 `(2, 3)`을 선택합니다.
4. 다음 회의의 시작 시간이 3 이상인지 확인합니다.
5. `(3, 4)`는 바로 이어서 진행할 수 있으므로 선택합니다.
6. `(1, 5)`는 이미 선택한 회의와 겹치므로 건너뜁니다.
7. `(4, 7)`은 시작 시간이 4이므로 선택합니다.
8. `(6, 8)`은 7 이전에 시작하므로 건너뜁니다.
9. `(8, 8)`은 7 이후에 시작하므로 선택합니다.
10. 총 4개의 회의를 진행할 수 있습니다.

```text
[종료 시간이 같으면 시작 시간 기준 오름차순 정렬]

  ↓
[회의 시작 시간 >= 현재 종료 시간인가?]

  ├─ 아니오 → [다음 회의 확인]
  └─ 예 → [선택한 회의 수 반환]
```

## 7. 기본 코드 템플릿

```python
def count_available_meetings(meetings):
    ordered = sorted(meetings, key=lambda meeting: (meeting[1], meeting[0]))

    count = 0
    last_end_time = 0

    for start_time, end_time in ordered:
        if start_time >= last_end_time:
            count += 1
            last_end_time = end_time

    return count


if __name__ == "__main__":
    sample_meetings = [
        (1, 5),
        (2, 3),
        (3, 4),
        (4, 7),
        (6, 8),
        (8, 8),
    ]

    print(count_available_meetings(sample_meetings))
```

### 코드 흐름 설명

* `ordered`는 종료 시간이 빠른 회의부터 정렬한 리스트입니다.
* 정렬 기준 `(meeting[1], meeting[0])`은 종료 시간을 먼저 보고, 같으면 시작 시간을 봅니다.
* `last_end_time`은 마지막으로 선택한 회의가 끝난 시간입니다.
* 다음 회의의 `start_time`이 `last_end_time` 이상이면 두 회의는 겹치지 않습니다.
* 회의를 선택하면 `count`를 1 늘리고, `last_end_time`을 현재 회의의 종료 시간으로 바꿉니다.
* 시작 시간과 종료 시간이 같은 회의도 조건상 선택할 수 있으므로 `>`가 아니라 `>=`를 사용합니다.

## 8. 시간복잡도와 공간복잡도

### 시간복잡도

* 회의를 정렬하는 데 `O(n log n)`이 걸립니다.
* 정렬된 회의를 한 번 순회하는 데 `O(n)`이 걸립니다.
* 전체 시간복잡도는 `O(n log n)`입니다.

여기서 가장 큰 비용은 정렬입니다. 회의를 선택하는 과정 자체는 한 번 훑는 정도입니다.

### 공간복잡도

* 정렬 결과를 새 리스트로 만들면 `O(n)` 공간이 필요합니다.
* 입력 리스트를 직접 정렬한다면 추가 공간은 더 줄일 수 있습니다.
* 선택 개수와 마지막 종료 시간만 저장하므로 핵심 변수는 `O(1)`입니다.

## 9. 예제로 이해하기

다음 회의 목록을 보겠습니다.

```text
meetings = [
  (0, 2),
  (1, 4),
  (2, 2),
  (2, 5),
  (4, 6),
  (6, 7)
]
```

종료 시간 기준으로 정렬하면 다음 순서로 볼 수 있습니다.

```text
(0, 2)
(2, 2)
(1, 4)
(2, 5)
(4, 6)
(6, 7)
```

처리 과정:

1. `(0, 2)`를 선택합니다. 현재 종료 시간은 2입니다.
2. `(2, 2)`는 시작 시간이 2라서 선택할 수 있습니다. 현재 종료 시간은 2입니다.
3. `(1, 4)`는 2보다 먼저 시작하므로 건너뜁니다.
4. `(2, 5)`는 시작 시간이 2라서 선택할 수 있습니다. 현재 종료 시간은 5입니다.
5. `(4, 6)`은 5보다 먼저 시작하므로 건너뜁니다.
6. `(6, 7)`은 선택할 수 있습니다.

최종 결과는 4개입니다.

이 예제는 시작 시간과 종료 시간이 같은 회의가 있을 때도 `start_time >= last_end_time` 조건을 사용해야 함을 보여 줍니다.

* 하나의 회의실, 하나의 사람, 하나의 기계처럼 동시에 하나만 처리할 수 있는 자원이 있습니다.
* 여러 구간 중 겹치지 않게 최대한 많이 선택해야 합니다.
* 각 항목에 시작 시간과 종료 시간이 있습니다.
* "최대 몇 개", "겹치지 않게", "배정" 같은 표현이 나옵니다.
* 모든 조합을 확인하면 시간이 부족할 만큼 입력이 큽니다.
* 빨리 끝나는 것을 먼저 고르면 남은 선택지가 넓어지는 구조입니다.

## 11. 비슷한 알고리즘과 헷갈리는 부분

### 시작 시간 기준 정렬과의 차이

시작 시간이 빠른 회의를 먼저 고르면 긴 회의가 앞을 차지할 수 있습니다. 이 문제의 목표는 빨리 시작하는 것이 아니라 많이 배정하는 것입니다.

그래서 종료 시간 기준 정렬이 핵심입니다.

### 회의 시간이 짧은 순서와의 차이

짧은 회의가 항상 좋은 선택은 아닙니다. 짧더라도 애매한 시간대에 있으면 앞뒤 회의를 막을 수 있습니다.

회의실 배정에서는 길이보다 "언제 끝나는가"가 더 중요합니다.

### 그리디와 완전탐색

완전탐색은 모든 회의 조합을 확인합니다. 회의실 배정은 종료 시간이 빠른 회의를 고르는 선택이 최적해를 보장하므로 그리디로 풀 수 있습니다.

### 우선순위 큐를 쓰는 회의실 문제와의 차이

회의실 하나에서 최대 회의 수를 구하는 문제는 정렬과 단순 순회로 충분합니다. 여러 회의실이 필요하거나 최소 회의실 개수를 구하는 문제는 우선순위 큐가 자주 사용됩니다.

## 12. 자주 하는 실수

* 시작 시간 기준으로 정렬해서 긴 회의를 먼저 선택합니다.
* 회의 길이가 짧은 순서로 정렬해 반례가 생깁니다.
* 종료 시간이 같을 때 시작 시간 기준 정렬을 고려하지 않습니다.
* `start_time > last_end_time`으로 비교해 바로 이어지는 회의를 놓칩니다.
* 첫 회의를 무조건 따로 선택하다가 회의 목록이 비어 있는 경우를 처리하지 못합니다.
* 선택한 회의의 종료 시간으로 `last_end_time`을 갱신하지 않습니다.
* 겹치는 회의를 건너뛰지 않고 개수를 증가시킵니다.
* 문제의 시간 조건에서 시작과 종료가 같은 회의가 가능한지 확인하지 않습니다.

## 13. 힌트 생성용 관점

### 1단계 힌트: 개념 힌트

겹치지 않는 회의를 최대한 많이 고르려면, 다음 회의를 넣을 시간을 많이 남겨야 합니다. 어떤 회의를 고르면 남은 시간이 가장 넓어질지 생각해 보세요.

### 2단계 힌트: 접근 힌트

회의를 종료 시간이 빠른 순서로 정렬해 보세요. 이미 선택한 회의가 끝난 시간 이후에 시작하는 회의만 고르면 됩니다.

### 3단계 힌트: 구현 힌트

`last_end_time` 변수를 두고, 정렬된 회의를 순회하세요. `start_time >= last_end_time`이면 회의를 선택하고 `last_end_time = end_time`으로 갱신합니다.

## 14. 언제 사용하면 좋은가

* 입력 조건: 시작 시간과 종료 시간이 있는 구간들이 주어질 때 좋습니다.
* 문제 유형: 회의실 배정, 활동 선택, 상담 일정 선택, 작업 구간 선택에 적합합니다.
* 자주 등장하는 표현: "겹치지 않게", "최대 개수", "한 회의실", "하나의 사람이 할 수 있는 활동"이 단서입니다.
* 적합한 자료구조: 회의 정보를 담는 리스트와 정렬을 사용합니다.
* 사용하면 안 되는 경우: 회의마다 중요도나 보상이 다르면 단순히 개수만 최대화할 수 없습니다. 이때는 동적 계획법이나 다른 최적화가 필요할 수 있습니다.

## 15. 요약 정리

* 회의실 배정은 겹치지 않는 회의를 최대한 많이 고르는 문제입니다.
* 가장 빨리 끝나는 회의를 먼저 선택하는 그리디 전략을 사용합니다.
* 정렬 기준은 `(종료 시간, 시작 시간)`입니다.
* 다음 회의는 `시작 시간 >= 마지막 종료 시간`일 때 선택할 수 있습니다.
* 전체 시간복잡도는 정렬 때문에 `O(n log n)`입니다.
* 시작 시간이 빠른 회의나 길이가 짧은 회의를 먼저 고르는 것은 정답을 보장하지 않습니다.
* 시작 시간과 종료 시간이 같은 회의도 선택 가능한지 조건을 정확히 확인해야 합니다.
